# 03 接入上游模型来源

「通道」（界面里也叫「来源」）就是一条上游：一个 `base_url` + 一个密钥 + 一组模型。
OneGate 的所有请求最终都落到某条通道上。**这一章不配通，`/v1` 永远是 503。**

## 3.1 先想清楚要接几条

- 一条也能用，只是那条挂了就全挂。
- 同一个模型配两条以上，OneGate 会自动加权轮询，并在某条失败时切到另一条。
- 不同厂商的模型名不一样（有的要带日期后缀），用「模型别名」抹平。

先准备好每个上游的三样东西：`base_url`、API Key、支持的模型名。

`base_url` 一般长这样，写不写结尾的 `/v1` 都可以（程序会自己处理重复）：

```
https://api.example.com/v1
```

> 换成一个真实的域名。教程里所有 `example.com` 都是占位。

## 3.2 建第一条通道

现在做什么：控制台 →「资源」→「渠道管理」→ 新建。

字段一个一个说，全部对应仓库里真实存在的字段：

| 界面字段 | 必填 | 填什么 / 限制 |
| --- | --- | --- |
| 渠道名称 | 是 | 你自己认得就行，例如 `官方主线路` |
| 权重 | 否 | 整数 ≥ 1，默认 1。同模型多条通道时按权重比例分流，2 就是被选中的概率翻倍 |
| BASE_URL | 是 | 必须是 `http://` 或 `https://` 开头，末尾多余的 `/` 会被去掉 |
| 路径前缀 | 否 | 上游要求额外子路径时填，例如 `openai`；首尾 `/` 会自动去掉，留空即可 |
| 上游 KEY | 是 | 上游的密钥。保存后**只显示掩码**（`sk-…abcd`），看不到明文 |
| 倍率 | 否 | 0.01–100，默认 1。这个来源的成本系数，见第 3.5 节 |
| 并发上限 | 否 | 0–512，默认 0 = 不限制。见第 3.4 节 |
| 超时（毫秒） | 否 | 1000–600000，默认 300000（5 分钟） |
| 排队等待（毫秒） | 否 | 0–60000，默认 0。并发满了以后最多等多久 |
| 排队人数上限 | 否 | 0–1000；并发上限 > 0 时默认 100 |
| 失败重试次数 | 否 | 0–2，默认 2 |
| 模型别名（JSON） | 否 | 形如 `{"gpt-4o":"gpt-4o-2024-11-20"}`，留空为 `{}` |
| 模型列表 | 是 | 这条通道支持的模型名。只有列在这里的模型才会被路由过来 |
| 自定义请求头（JSON） | 否 | 上游需要额外头时用，例如 `{"X-Trace":"on"}`，留空为 `{}` |

填一个最小例子：

```
渠道名称      官方主线路
权重          1
BASE_URL      https://api.example.com/v1
上游 KEY      sk-your-upstream-key
模型列表      gpt-4o-mini
其余           保持默认
```

点保存。

看到什么算成功：列表里出现这条通道，密钥显示成 `sk-…` 加末四位，没有被标成红色/报错。

失败了先查什么：

| 报错 | 原因 |
| --- | --- |
| `base_url must be HTTP(S) and api_key is required` | `base_url` 没写协议头，或上游 KEY 空着 |
| `并发上限 需为 0 到 512 之间的整数` | 填了小数或超出范围；这一类数字字段都只收范围内的整数（倍率除外） |
| `自定义请求头必须是 JSON 对象` / `模型别名必须是对象…` | 这两个框只收 JSON，不要写 `X-Trace: on` 这种形式 |

## 3.3 先点一次「测试」

不要等发出去第一个请求才发现上游 Key 是错的。通道卡片上有「测试」按钮。

它做的事很具体：拿这条通道里**第一个不是 `*` 的模型**发一次 `max_tokens: 1` 的探测请求，
返回耗时和错误信息。

看到什么算成功：显示成功 + 一个延迟毫秒数。

失败了先查什么：

| 现象 | 先查 |
| --- | --- |
| 上游 401 / 403 | 上游 KEY 错了或过期了；这家服务是否需要额外的头（用「自定义请求头」补） |
| 上游 404 | `base_url` 或「路径前缀」拼错了；或者模型名上游不认 |
| 超时 | 服务器出网被限制、上游太慢，或 `base_url` 指到了内网不可达地址 |
| 一直转圈 | 看服务端控制台/`journalctl`，通常是 DNS 或 TLS 失败 |

> 测试只验证「这条通道能不能通」，不会把结果记进调用记录，也不扣额度。

## 3.4 并发上限到底在保护什么

每个上游都有它能同时接多少个请求。超过以后轻则排队、重则报错，甚至封号。
「并发上限」就是在这里踩刹车。

- `0` = 不限制（默认）。适合你完全信任上游、或者自己有别的限流。
- `> 0` = 这条通道同时最多处理这么多个请求；再多就排队，等「排队等待」毫秒；
  还没轮到就返回 429 `concurrency_limit_exceeded`。

建议起步值：对免费额度或小配额的上游，先设 4–8；商用大配额可以设 32 或更高。

看到什么算成功：并发起来以后，超出的请求得到 429，客户端收到明确的 JSON 错误而不是挂死。

失败了先查什么：如果正常业务量就频繁 429，说明上限设低了；如果上游在告警你超限，
说明上限设高了。这两个方向相反，看日志里 429 和上游错误哪个多。

## 3.5 超时与重试：别把用户挂在半路

- **超时**：单次上游请求最多等多久，默认 300 秒。对话类业务建议 60–120 秒，
  比客户端自己的超时略长一点即可。最大 10 分钟。
- **重试次数**：0–2。只对「可重试」的错误重试：HTTP 429 和 5xx。上游 401/403/400 这类
  **不会重试**，会直接返回给客户端，避免把错误请求重复打给上游。
- 重试时会重新选通道，所以配了两条以上通道时，重试的意义是「换一条再试」。
- 一次请求最多尝试 3 次（首轮 + 2 次重试），通道失败后该通道会进入冷却，
  冷却时间从 30 秒起、逐次翻倍、最长 300 秒，冷却期内不会被选中。

看到什么算成功：你故意把一条通道的上游 Key 改错，同一模型的另一条通道能接住请求。

失败了先查什么：全都失败时才返回 502 `upstream_error`，此时要看的是「每条通道都错在哪」，
而不是客户端参数。

## 3.6 倍率：成本口径，不是售价

「倍率」是这条来源的成本系数，用来表达「这条线路比标价贵/便宜多少」。
计费公式（看代码可以核对）：

- 下游独立密钥：`模型价格 × 来源倍率 × 密钥组倍率`
- 门户账户密钥：`模型价格 × 用户组倍率`（来源倍率在这一条路径上不重复乘）

也就是说，同一份价格表，接到贵线路上成本自然更高，不用维护两套价格。
倍率范围 0.01–100。

看到什么算成功：调用记录里同模型、同 token 数，两条不同倍率的通道，成本数字按倍率比例不同。

失败了先查什么：成本是 0 —— 先去「设置」里确认这个模型有价格；没有价格时成本记 0，额度不扣。
这是设计行为，不是 bug。

## 3.7 模型别名：客户端名和上游名不一样怎么办

场景：客户端一直发 `gpt-4o`，你接的上游只认 `gpt-4o-2024-11-20`。

模型别名填：

```json
{"gpt-4o": "gpt-4o-2024-11-20"}
```

含义是「客户端发 `gpt-4o` 时，实际请求上游用 `gpt-4o-2024-11-20`」。
别名会被自动补进这条通道的模型列表，所以模型列表里没写 `gpt-4o` 也能路由到。

看到什么算成功：用客户端名调用返回 200，调用记录里的 `model` 是客户端发的名字。

失败了先查什么：仍然 503 —— 检查别名 JSON 有没有语法错误（少引号、用了中文引号），
保存时会直接报错，不会静默忽略。

## 3.8 一个模型配多条通道

现在做什么：再建一条通道，模型列表里写**同一个模型名**，权重按你想要的流量比例给。

```json
{
  "name": "备线",
  "base_url": "https://api2.example.com/v1",
  "api_key": "sk-your-upstream-key-2",
  "models": ["gpt-4o-mini"],
  "weight": 1
}
```

看到什么算成功：「模型广场」里这个模型的「可用通道数」≥ 2；连续调用几次，
调用记录里的通道名会在几条之间轮换。

失败了先查什么：只有一条被用到 —— 另一条是不是 `enabled` 关了、是不是在冷却期
（刚失败过）、模型名是否拼得一模一样（大小写、多余空格都算不同）。

## 3.9 用配置导入（可选）

通道多的时候，一条条点很慢。控制台背后的接口支持整包导入：

`GET /admin/api/sources/config` 取当前配置（密钥是掩码），`PUT` 同样的结构提交。
仓库里 `config/sources.example.json` 就是这个格式的示例，可以照着改。
它还会一起带上「来源组」（`source_groups`，把若干通道归成一组便于查看健康度）。

现在做什么：先取一次现有配置，看清楚结构再提交。

```bash
curl -s -b /tmp/onegate.cookie http://127.0.0.1:8787/admin/api/sources/config
```

看到什么算成功：返回里有 `sources` 数组，字段和界面上一一对应。

失败了先查什么：401 —— Cookie 过期了，重新登录一次（`POST /admin/login`）。
PUT 时 `sources` 里每一项都必须有可用的 `api_key`，且**全部校验通过才会整体生效**，
有一条不合法就整包拒绝，不会写一半。
